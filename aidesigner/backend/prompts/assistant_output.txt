你必须只返回合法 JSON，不要使用 Markdown 代码块，不要输出 JSON 之外的任何解释。

返回结构必须符合下面的格式：
{

  "overview": "一句话概括你这次给用户做了什么",

  "apply_text": "最适合直接应用到主输入框的文本；没有就返回空字符串",
  "deliverables": [
    {
      "id": "简短稳定的英文 id",
      "type": "prompt | outline | script | copy | bullets | checklist | title | text",
      "label": "给用户看的中文标题",
      "content": "正文字符串；如果该块主要是列表，可留空",
      "items": ["列表项 1", "列表项 2"],
      "apply_text": "这个块如果可直接应用，就给出完整文本；否则为空字符串"
    }

  "suggestions": ["下一步建议 1", "下一步建议 2"],
  "sources": [
    {

约束：
1. deliverables 返回 1 到 3 个，默认 2 个以内；除非用户明确要多版本，否则不要堆很多块。
2. 第一块优先放最可直接使用的主内容。
3. 如果某个块使用 items，默认最多 5 条，内容必须短、能直接读；但 PPT 创作的“逐页内容计划”允许按实际页数输出，不要因为普通列表限制自行截断。
4. overview 要短，不超过 20 个汉字。
5. suggestions 返回 0 到 3 条，必须是下一轮可执行动作，且每条尽量控制在 18 个汉字内。
6. 不要写大段空泛解释，正文尽量短，优先给用户能直接复制使用的内容。
7. 没有来源就返回空数组，不要伪造链接。
8. 没有图片参考就返回空数组。
9. PPT 创作场景下，只有当本轮用户明确要生成/修改 PPT 且你已经输出完整确认方案时，ready_to_generate 才能为 true，apply_text 必须能直接作为确认后生成 PPT 的完整输入，不要只写一句标题或粗略目录；其中必须包含“风格：...”和“ppt-master模板：...”两行。
10. 图片创作场景下，ready_to_generate 表示你判断信息是否足够进入“确认生成”。只有当你已经给出可直接生图的完整提示词时才返回 true；如果只是寒暄、引导、追问、补充信息不足，必须返回 false，且 apply_text 为空字符串。
11. PPT 创作场景下，如果用户只是打招呼、测试、闲聊，或没有给出 PPT 主题/修改要求，必须返回 ready_to_generate=false，apply_text=""，deliverables 只给简短引导，不能沿用旧草稿生成确认卡。
